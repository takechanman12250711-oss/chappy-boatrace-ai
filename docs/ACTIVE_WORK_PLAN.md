更新日: 2026-08-18
基準: GitHub `main`

## 最終目的

収集・分析そのものを完成扱いにしない。締切前の実戦データと公式結果を使い、改善案を検証し、承認済みの改善を本番予想へ反映し、反映後の的中率・回収率・収支まで確認して、実戦で使える予想アプリを完成させる。

## 開発確認順序

1. GitHub `main`
2. 未マージPR
3. 本台帳
4. 既存の採用済み・棄却済みPR
5. 各ゲート・統計レポート
6. 過去の申し継ぎ・資料

資料や記憶だけで「未実装」と判断しない。同目的の過去検証が存在する場合は再実施しない。

## 絶対ルール

- 完了済み機能を別名・別Phase・別スクリプトとして作り直さない。
- 過去の公式締切前データ・保存済み分析結果を捨てて0Rからやり直さない。
- prospective A/Bは将来再現確認として使い、過去の正式根拠を消さない。
- 診断件数が多いだけで根本原因と断定しない。`miss-cause-analysis` は `causalClaim=false` を前提に扱う。
- A/B・回帰・holdout等で改善が確認され、明示承認された変更だけ本番予想へ反映する。
- 予想ロジック・買い目・配点・UIの変更は明示承認なしに行わない。
- 採用済み改善は反映後成績を確認する。悪化時は補正を重ねず対象変更を戻す。
- 不具合修正は改善作業と混ぜず `BUG-xxx` として別管理する。

## 現在の主線

1. 最新1,450Rの改善調査候補を、採用済み・棄却済み・検証中・未処理へ照合する。
2. 採用済み/棄却済みの同目的作業は閉じたまま再開しない。
3. 本当に未処理で、既存データから検証可能な1件だけを選ぶ。
4. 既存データでA/B・回帰・期間分割・holdoutを確認する。
5. 改善が確認された場合だけ、変更前後・影響・戻し方を提示して承認を得る。
6. 承認後、1目的1PRで本番予想へ反映する。
7. 反映後の実戦成績を確認し、改善なら維持、悪化ならロールバックする。
8. 次の未処理候補へ進む。

## 「改善1件完了」の定義

以下を全部満たした時だけ完了とする。

原因候補特定 → 過去検証との重複確認 → 改善案 → A/B/回帰/holdout → 明示承認 → 本番反映 → 反映後実戦確認 → 継続または撤回確定

データ収集、分析レポート生成、Phase完了、PRマージだけでは「予想改善完了」としない。
