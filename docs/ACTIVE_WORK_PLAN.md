# チャッピーボートレースAI ACTIVE WORK PLAN

更新日: 2026-08-18
基準: GitHub `main`

## 目的

この文書は、完了済み工程の再実装・別名での作り直し・途中工程の重複着手を防ぐための唯一の作業台帳として使用する。

開発確認順序は必ず以下とする。

1. GitHub `main`
2. 未マージPR
3. 本台帳
4. 各ゲート・統計レポート
5. 過去の申し継ぎ・資料

資料や記憶だけを根拠に「未実装」と判断してはならない。

## 絶対ルール

- 現在の工程が完了するまで別工程へ進まない。
- 完了済み機能を別名・別Phase・別スクリプトとして作り直さない。
- 新しい作業を始める前に `main` と本台帳を検索し、同目的の既存実装がないことを確認する。
- 予想ロジック・買い目・配点・UI・主要機能は、明示承認なしに変更しない。
- A/B候補が必要件数未到達の間は本番ロジックを変更しない。
- 自動収集・自動更新コミットを新規実装作業と混同しない。
- 不具合修正は改善作業と混ぜず `BUG-xxx` として別管理する。

## 次工程

### DEC-01 必要件数到達後の判定

開始条件: 各検証が所定の30Rまたは100Rへ到達した場合のみ。

判定は既存統合ゲートの以下5種類を使用する。

- `continue`
- `candidate`
- `reject`
- `review`
- `blocked`

処理:

- `continue`: 追加収集。コード変更なし。
- `reject`: B案終了。コード変更なし。
- `review`: 原因分析のみ。本番変更なし。
- `blocked`: データ・安全条件の不備のみ修正。
- `candidate`: APR-01へ進む。

`continue` または `reject` となった検証を、名前を変えて同じ目的で再作成してはならない。

### APR-01 採用候補レビュー

開始条件: `candidate` が1件以上発生した場合のみ。

提示必須項目:

1. 変更内容
2. 現在仕様
3. 変更後仕様
4. 対象レース数
5. Aの的中率・回収率・収支
6. Bの的中率・回収率・収支
7. 場別悪化の有無
8. メリット
9. デメリット
10. 元へ戻す方法
11. 予想・買い目・UIへの影響

明示承認前は `automaticApplication=false` / `usableForPrediction=false` を維持する。

### IMP-01 承認済み候補の実装

開始条件: APR-01で明示承認された1件のみ。

固定手順:

1. 1候補だけ選択
2. 専用ブランチ作成
3. 変更前テスト
4. 1目的だけ変更
5. 構文・回帰・A/Bテスト
6. PR作成
7. 内容確認
8. `main` へマージ
9. 本番確認

複数理論を同一PRで同時変更しない。

### VAL-01 本番反映後の監視

開始条件: IMP-01完了後。

監視項目:

- 的中率
- 回収率
- 収支
- 対象レース数
- 場別悪化
- 本線と穴のバランス
- 買い目点数
- 見送り件数
- エラー・表示崩れ

悪化した場合は新しい補正を上乗せせず、まず対象変更の撤回・ロールバックを検討する。

## 不具合割り込みルール

新しい実機不具合だけ `BUG-xxx` として割り込ませる。

対象例:

- 画面が開かない
- 買い目が表示されない
- 結果が保存されない
- 別レースのオッズが混ざる
- 本命と押さえが逆転する
- 同じ処理が二重実行される

着手前に `main` と過去PRを検索し、同じ不具合修正が既に存在しないことを確認する。

## 禁止事項

- Phase3・Phase4・Phase5の再構築

- 公式結果照合経路の再構築

- 未完了作業を残したまま別工程へ移動
