# チャッピーボートレース開発

## 現在地を一度で合わせる

- 対象は `takechanman12250711-oss/chappy-boatrace-ai`。確認順は最新のGitHub main → 関連する最新PR → この会話の申し継ぎ → 過去資料とする。古いSHA、PR番号、点数上限、完了報告を固定値として使わない。
- 「続き」「進めて」は、この会話で合意した未完了作業を引き継ぐ。追加要望は元の目的に組み込み、勝手に別の開発課題へ移らない。
- 対象コード・呼び出し元・必要な実行結果を絞って読み、既存処理と未接続部分を分ける。ファイルがあるだけで画面から使える、定期実行済み、公開済みとは判断しない。
- 同じmainと対象を確認済みなら再度の総点検を始めない。進捗質問には確認できた事実と残りを回答し、実装依頼なら差分を作る。関連ファイルを探すときだけ [project-map.md](references/project-map.md) を読む。

## 既存資産と代替手段を先に使う

- 作業開始時に、対象機能の既存Skill、ドキュメント、実装、接続済みPlugin/Connectorを確認する。既存機能がある場合は再実装せず、未接続部分・不具合・不足条件だけを直す。特にnote作業では `chappy-note-*` と `docs/note-automation.md` を先に確認する。
- 外部サービス操作が必要な場合は、独自の認証・ブラウザ操作を作る前に、利用可能な正規Plugin/Connector、公式連携、既存のログイン済み経路を比較する。適合する既製手段があれば優先する。接続済みでないものを接続済みと扱わない。
- 同じ障害・同じ前提の方式で2〜3回失敗したら、その方式への追加修正をいったん止める。原因だけでなく代替方式を比較し、本来の目的を最短で達成できる方式へ切り替える。同じ操作を言い換えてユーザーに繰り返させない。
- ユーザー本人のログイン、Face ID、2段階認証など本人操作が必要な検証は、こちら側で成立条件を確認してから最後にまとめて依頼する。途中の試行錯誤のために同じ本人操作を何度も要求しない。
- 新しい方式へ切り替える前に、既存データ・既存設定・既存アカウントの変更が本当に必要か確認する。目的達成に不要なら変更しない。

## 変更中に守ること

- 優先順は **展開 → コース → ST/スリット → 展示/足 → 残し/拾い → 当地/水面 → 技量 → モーター**。
- オッズは買い目作成後に扱う。オッズ不足や検査合格のために買い目を削除・差し替えない。点数などの具体値は最新の憲章と実装から確認し、通常候補・実戦厳選・参考/万舟を混同しない。
- 既存の予想・公式結果・理論検証データを捨てたり、過去予想を結果に合わせて書き換えたりしない。新方式の検証は原本を保持して別に保存する。派生データの再構築と原本変更を区別する。
- 予想基準、学習の自動採用、UI構成を依頼なしに変えない。新聞UIは追加しない。画面修正は依頼対象だけを直し、既存の導線・部品を再利用する。
- 無料方針を維持し、Claudeの追加契約や有料AI APIを前提にしない。Skillは手順の共有であり、常時稼働や他のAIの起動・認証を意味しない。

## 依頼を反映まで進める

1. 合意した変更と完了条件を短く示し、作業中の差分を保護してブランチ上で実装する。既存機能を再実装せず、未接続・不具合だけを直す。
2. 保存・非同期操作・期限判定など、変更に伴う具体的な失敗リスクと必須CIを検証する。文章だけの小変更に実装をなぞるテストを増やさない。
3. GitHubへの反映が会話で許可されている場合は、PR作成 → 必要なCI合格 → 意図したheadでマージ → main差分確認まで進める。Skill自体を外部変更の許可とは扱わない。認証がない手段を繰り返さず、利用可能な正規の接続を使う。
4. CI失敗は原因を絞って修正する。合格後に理由なく検査を広げたり繰り返したりしない。main反映済み、実行待ち、本番実行確認済みを分けて報告する。
5. 何が使えるようになったか、検証と反映の状態、残る具体的な作業を簡潔に伝える。部分完了を全体完成と呼ばない。

## note作業の振り分け

noteの選定・原稿・監査・公開・結果照合には、必要なものだけ `chappy-race-select`、`chappy-note-generate`、`chappy-note-audit`、`chappy-note-publish`、`chappy-note-settle` を使う。利用環境にない場合はリポジトリ内の共有版を確認する。

note自動公開は、最新mainで実装・接続・権限・投稿条件が確認できるまで実行済みとしない。生成側の `publishable` や過去の監査合格を公開許可と取り違えない。開発用Skillから公開停止を解除しない。
