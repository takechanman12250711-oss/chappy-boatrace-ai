# 検証後のPRマージ（積み重ねPRを含む）

正本は `docs/development-approval.md`。2026-11-19の本人指示により、依頼済み実装・修正・研究保存・検証・main反映は、個別マージ承認のボタンを毎回求めず完了まで進める。本人が特定PRの個別確認・保留を明示した場合だけ、正本の任意確認手順に従う。

## マージ前の確認

- 現在headのCIがすべて完了・成功し、独立レビューが完了して未解決の指摘がないことを確認する。古い取消runに対応する同じheadの新runが成功していれば、その事実を記録する。
- Codexが利用できなければ未実施と明記し、利用可能な独立レビュー経路で確認する。未実施をレビュー成功へ読み替えない。
- 外部障害・権限不足・利用枠不足はログで原因を確認する。依頼範囲の修正・既存の代替経路で解消できれば進める。必要なCIが成功せず解消不能なら不足を報告し、チェックや権限を緩めたり、課金を追加したりしない。
- 利用中のAuto-fixを停止し、進行中修正の終了を確認する。
- 同じPRの番号・タイトル・作業開始base・固定head・照合時main・検証・レビュー・影響・未確認点を記録する。「このPRをGitHubで確認」は任意の読み取り導線とし、資料提示を個別許可待ちのゲートにしない。

## head/main照合から反映まで

1. PRとmainを再取得し、対象リポジトリ、PR番号、main向けbase、現在headが検査・レビュー対象と一致することを確認する。
2. mainが照合時から進んでいれば、変更ファイルと依存影響を確認する。非重複で依存影響もなければ理由を記録して続行できる。重複・依存変更があれば最新mainを取り込み、新headの必要な検査・レビュー・CIを行う。既に依頼された作業を個別再承認待ちへ戻さない。
3. GitHubのrequired checks・required reviews・権限・マージ可能状態を確認し、必要ならDraftを解除する。`PUT /repos/{owner}/{repo}/pulls/{n}/merge` を `sha` 固定・squashで実行する。不一致で拒否されたら更新と再照合へ戻る。自己Approveや要件緩和は行わない。
4. マージ状態・マージcommit・main反映を読み戻して報告する。サイト公開は既存の `pages build and deployment` の成功で別に確認する。

## 積み重ねPR（A→B→C…）

- 1つずつ順にマージする。次のPRは前のPRのブランチをbaseにして作っておく。
- 前のPRをsquashでマージしたら、次のブランチへ最新mainを取り込む。同じ内容のadd/add競合は内容が同じことを確認して次のブランチ側を残す。自動更新されるdataの生成ファイルはmain側を使う。
- `PATCH /pulls/{n}` でbaseをmainへ付け替え、新headの必要な検査・レビュー・CIを確認して、上の照合と反映へ進む。ボタン承認を必須にしない。
- 前のPRを修正したら後ろのブランチへ順に取り込んでpushする。テストの追記が競合したら両方を保持し、検査してからpushする。
- 生成データ（`data/stats/*.json` など）はPRに含めない。マージ後に既存workflowが再構築する。

## 実行範囲と確認

- 研究PRの反映と本番採用は区別し、採用には別変更として必要な検証・採用gate・封印条件を守る。採用まで既に本人依頼なら再承認待ちにしない。研究結果だけで無検証に採用しない。
- 新課金・実購入・履歴削除など未依頼行為へ許可を広げず、原本・会計・認証境界を維持する。新しい自動マージbot・workflow・定期監視を追加しない。
- CIは `GET /commits/{sha}/check-runs` など既存の確認経路で対象headの全件を確認する。長い検査では進捗を伝え、古いheadの成功を転用しない。
- ブランチ追跡がなく「未push」に見える場合は `git fetch origin +refs/heads/<b>:refs/remotes/origin/<b>` で照合する。
