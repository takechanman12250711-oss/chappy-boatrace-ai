# PRの承認ボタンとマージ（積み重ねPRを含む）

正本は `docs/development-approval.md` の「会話のボタンでマージを承認する」。この手順はそれを実際に回すための手引き。

## ボタンを出す条件
- 現在headのチェックがすべて完了・成功。
  - 外部サービスの停止（例：Vercel の 402 Payment Required）で落ちたチェックは、失敗の理由をログで確かめ、本人に伝えて進め方を選んでもらう（例：そのチェックが走る原因になった変更を外す）。条件を勝手に緩めない。
  - 同じチェックの古いrunが自動で中止（cancelled）され、同じheadの新しいrunが成功している場合は、その事実を質問文に書く。
- Codexレビュー：この環境で実行できなければ「未実施」と質問文に書く。
- 質問文：PR番号・タイトル・固定head（短縮）・照合base（今のmain）・CI結果・レビュー・本番の予想/買い目への影響。選択肢は「マージする」「保留」。

## 「マージする」の後
1. PRのheadを取り直し、固定headと一致を確認。
2. main が照合baseから進んでいたら、変わったファイルを列挙。`data/` だけで、PRの変更ファイルと重ならなければ続行。重なれば最新mainを取り込み、CIをやり直して再提示。
3. `PUT /repos/{owner}/{repo}/pulls/{n}/merge` を `sha` 固定・squash で実行。
4. main 反映を確認して報告。サイト公開は `pages build and deployment` の成功で別に確認する。

## 積み重ねPR（A→B→C…）
- 1つずつ順にマージする。次のPRは前のPRのブランチを base にして作っておく。
- 前のPRを squash でマージしたら、次のブランチへ最新 main を取り込む。同じ内容の add/add 競合が出たら、**次のブランチ側（ours）**を残す（前のPRの内容＋自分の変更を持っているため）。自動更新される `data/` の生成ファイルは main 側を使う。
- `PATCH /pulls/{n}` で base を `main` に付け替え、新しいheadのCIを待ってからボタンを出す。
- 前のPRを修正したら、後ろのブランチへ順に取り込んで push する。テストファイルで両方の追記が競合したら、両方のテストを残してテストを実行してから push する。
- 生成データ（`data/stats/*.json` など）は PR に含めない。マージ後にワークフローが作り直す。

## 確認のしかた
- CI：`GET /commits/{sha}/check-runs`（全件 completed になるまで待つ。20〜30分かかるチェックがある）。
- 待つときは、条件が満たされたら終わる `until` ループをバックグラウンドで回す。
- ローカルのブランチ追跡が無いと「未push」に見えることがある。`git fetch origin +refs/heads/<b>:refs/remotes/origin/<b>` で照合する。
